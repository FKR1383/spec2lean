## 4. Proposed minimal architecture

This section proposes the minimal architecture components required for the future formalization of `and.b32`. No Lean code is written; each component states its source grounding and the proposed design.

- DESIGN CHOICE (D-1) — PTX instruction representation: a structured instruction form with fields: optional guard (`@{!}p`), mnemonic (`and`), type specifier (`.b32`), destination operand, and a source operand list (`a`, `b`). Grounding: SF-A2, SF-A11, SF-A12, SF-A13.
- DESIGN CHOICE (D-2) — Operand categories for the bounded base form: (a) destination register, (b) source register, (c) source constant immediate. A bit-bucket destination `_` is a candidate alternative destination form (see OQ-2). Grounding: SF-A2 (three-operand syntax), SF-A8 (register operands in the first `.b32` example; immediate source `0x80000000` in the second `.b32` example of the same section), SF-A13 (bit bucket), E-A26 (immediate `1` in a program-context `and.b32`).
- DESIGN CHOICE (D-3) — Scalar type and width representation: a fundamental type is represented as a pair (basic type, size in bits); `.b32` maps to (Bits/Untyped, 32). A minimal type lattice is needed only up to the types that `and.b32` and its operand-compatibility rule require. Grounding: SF-A14, SF-A15, SF-A16, SF-A5.
- DESIGN CHOICE (D-4) — Register/value representation: register variables always carry a fundamental type (SF-A14); values for `.b32` live in a fixed-width 32-bit untyped bit-value domain; a register file maps register names to values of their declared type. Predicate registers are 1-bit (SF-A16) and are mapped to a two-valued domain by design (D-13). Grounding: SF-A14, SF-A16, SF-A18, SF-A19.
- DESIGN CHOICE (D-5) — Minimal machine state: for the bounded base scalar `and.b32`, the state contains only a value-register file and a predicate-register file. No memory state space, shared state, or special-register state space is required by the bounded base form. Grounding: SF-A2 (base form `and.type d, a, b;` has no memory/sreg operand), SF-A3 (destination is a register), SF-A16 (`.reg` state space).
- DESIGN CHOICE (D-6) — State reads and destination update: source operand values are read from registers or constant immediates; when the instruction executes, the destination register is updated with the bitwise-and of the source values (candidate semantic content recorded as SF-A4 `d = a & b;`); when the complete guard expression evaluates false, the state is unchanged. Grounding: SF-A4, SF-A12, SF-A20; the guard-false consequence is an interpretation recorded in Section 11 (A-4) and Section 13 (OQ-3).
- DESIGN CHOICE (D-7) — Guard/predication architecture: the guard is an optional `.pred`-typed register reference, optionally negated (`@!p`); presence of a guard makes execution conditional; absence makes execution unconditional. Grounding: SF-A11, SF-A12, SF-A13.
- DESIGN CHOICE (D-8) — Execution-result / outcome representation: an instruction-local outcome type with at least two cases — "executed" (with updated state) and "guard false" (no state change). No error constructor is proposed yet because the official source read defines no exceptional behavior for the bounded base `and.b32` form (see A-6).
- DESIGN CHOICE (D-9) — Version and target-restriction representation for the base `and.b32` form: a record pairing a PTX ISA version bound ("introduced in" version) with a target requirement. For base `and.b32`: introduced-in PTX ISA 1.0; target requirement "all target architectures". Grounding: SF-A6, SF-A7.
- DESIGN CHOICE (D-10) — Traceability representation: every semantic claim carries (document identity, specification version, section heading, HTML anchor, HTML line range, source SHA-256). Grounding: SF-A1 and the evidence index in Section 14.

## 6. Register, value, and state foundations

The register/value/state architecture is grounded in the official register and type sections read in this pass (Section 5.1.1 Register State Space; Section 5.2.1 Fundamental Types; Section 5.4 variable declaration; Section 5.4.6 Parameterized Variable Names).

- DESIGN CHOICE (D-11) — The value domain for `.b32` is proposed as a fixed-width 32-bit untyped bit-value domain (e.g., 32-bit bit vectors); the exact Lean representation is a Lean-mapping decision outside this artifact. This differs from an unsigned-integer domain because `.b32` is the "Bits (untyped)" basic type (SF-A14) and the logic/shift family is described as "fundamentally untyped, performing bit-wise operations" (SF-A9).
- DESIGN CHOICE (D-12) — Registers are represented by names (identifiers) mapped to values, not by values alone, to support declaration typing and destination updates. Register references are by name rather than address because the official source states that registers are not fully addressable (SF-A16).
- DESIGN CHOICE (D-13) — Predicate register values are represented by a two-valued (boolean-like) domain, grounded in the official statement that predicate registers are 1-bit (SF-A16) and in the boolean-style use of predicates in `setp` examples (SF-A12). The exact encoding of "1-bit" into a Lean value domain is a Lean-mapping decision (see A-7, OQ-5).
- DESIGN CHOICE (D-14) — The minimal state for the bounded base `and.b32` is the pair (value-register file, predicate-register file). No memory state space, special-register state space, or other state space is included because the bounded base form has no memory or special-register operands and its description writes only to a destination register (SF-A2, SF-A3). The official `.reg` state-space text (SF-A16) supports the register-file model, and the rule that predicate variables may only be declared in the register state space (SF-A18) supports placing predicate registers in the same overall register state space rather than a separate one.
- DESIGN CHOICE (D-15) — Compilation-level and ABI notes in the register section (register spilling, function-scope restriction, legacy module-scope handling, alignment for multi-word loads/stores; SF-A16) are not modeled in the instruction-local architecture for `and.b32`. Whether any of these affect a future program-level semantics is an open question outside the bounded unit (OQ-6).

## 7. Operand architecture

- DESIGN CHOICE (D-16) — The bounded base `and.b32` form has exactly three operands in the order `d, a, b` (SF-A2). The operand-position roles of section 9.2 (destination `d`; sources `a`, `b`) apply (SF-A13). The official examples `and.b32  x,q,r;` and `and.b32  sign,fpvalue,0x80000000;` (SF-A8) show the three-operand shape with register and immediate sources; the description "Compute the bit-wise and operation for the bits in `a` and `b`" (SF-A3) is satisfied by register and immediate sources.
- DESIGN CHOICE (D-17) — Source operands `a` and `b` may be register variables or constant immediates. The `and` section itself shows an immediate in the `.b32` form: `and.b32  sign,fpvalue,0x80000000;` (SF-A8), and a program-context `and.b32` with an immediate source `1` appears in the mbarrier example (E-A26). The sibling `or` example `or.b32  mask mask,0x00010001` (SF-A10) corroborates immediates in the family. An immediate is modeled as a constant whose size is compatible with the instruction type under SF-A15. ## 8. Predication architecture

Predication is expressed uniformly by evaluation of the complete guard expression. The complete guard expression is: "true" when no guard is present; the value of the predicate register `p` for `@p`; and the negation of the value of `p` for `@!p`.

- DESIGN CHOICE (D-19) — Guard evaluation rule: an instruction executes if and only if its complete guard expression evaluates true. Cases: no guard — the complete guard expression is true and the instruction executes unconditionally (SF-A12); `@p` — the complete guard expression evaluates to the value of predicate `p` (SF-A12); `@!p` — the complete guard expression evaluates to not (value of `p`) (SF-A12).
- DESIGN CHOICE (D-20) — No state update is proposed only when the complete guard expression evaluates false. This single rule covers `@p` (no update when `p` is false) and `@!p` (no update when `not p` is false, i.e., when `p` is true), and it is the only guard-false consequence used in this architecture (D-6, D-8, A-4, OQ-3).
- DESIGN CHOICE (D-21) — A guard refers to a `.pred`-typed predicate register variable in the register state space (SF-A12, SF-A18). The guard is written with an `@` prefix to the left of the opcode (SF-A12, SF-A13). The `st.param`/`ld.param` predication exception (SF-A21) does not mention `and`.
- Predication is applicable to `and`: "All PTX instructions may be predicated" (SF-A11). No `and`-specific predication example was found in a literal search (A-9), and none is required because the general rule governs.
